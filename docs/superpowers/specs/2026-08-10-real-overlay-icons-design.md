# Circuit-Sword Real Overlay Icons — Design

Replaces the hand-authored 5×7 bitmap pixel-art icons (shipped earlier
today, `docs/superpowers/specs/2026-08-10-overlay-icons-design.md`) with
real vector icons: battery/WiFi from Batocera's own EmulationStation,
volume/brightness newly hand-drawn in the same flat-silhouette style and
16×16 canvas. Also changes `circuitsword-quickmenu`'s row layout so the
icon and its percentage bar sit on one line instead of two.

## Context

The previous 5×7 pixel-art icons look rough ("vieze pixel icoontjes",
user's words) — the grid was too small to draw recognizable shapes. This
design replaces them with real artwork instead of a bigger hand-drawn
grid.

One real, appropriately-licensed source was confirmed this session, plus
two new icons hand-drawn to match it:

- **Battery + WiFi**: `batocera-linux/batocera-emulationstation` (already
  the upstream source this project's own `batocera-emulationstation.mk`
  fetches at build time) ships real SVG icons at
  `resources/battery/{25,50,75,full,empty,incharge}.svg` (16×16 viewBox,
  flat white-fill silhouettes — 6 distinct battery states, richer than
  this project's previous 4-level scheme) and `resources/network.svg`
  (64×64 viewBox, single WiFi glyph, no on/off variant).
- **Volume + brightness**: no equivalent exists in Batocera/ES's own icon
  set. The original manufacturer firmware's `cs-hud` has small
  (14×11px) raster icons for both (`ICON_VOLUME.png`, `ICON_BRIGHTNESS.png`)
  — an early version of this design used those directly, but a visual
  preview (built and reviewed with the user before any implementation)
  showed they read as noticeably rougher than the crisp battery/WiFi
  vectors next to them. Revised to two newly hand-drawn SVG icons instead
  — a speaker-with-sound-waves for volume, a sun-with-rays for brightness
  — on the same 16×16 canvas, flat white fill/stroke, matching visual
  weight to the battery/WiFi set. Confirmed with the user against the
  rendered preview before finalizing.

Confirmed with the user via brainstorming (and a rendered visual preview
of every icon, on the actual black background and color palette, before
any code was written):
- Battery/WiFi icons come from Batocera/ES's own art (visual consistency
  with the rest of the OS); volume/brightness are new icons drawn to
  match that same style, once Kite's original raster art was seen
  side-by-side and judged inconsistent.
- Volume/brightness have no level-specific icon variants — the icon stays
  static; the existing percentage bar (already drawn in
  `circuitsword-quickmenu`, unaffected by this design) is what
  communicates the level. This is *why* the layout change below moves
  the bar onto the same line as the icon — with no text label anymore,
  a single static icon plus an adjacent bar reads naturally as one
  control.
- WiFi has no off-state variant in the source art — off is drawn as the
  same glyph in `QM_COLOR_DIM` (already this project's established
  "unselected/inactive" tint) rather than a second icon.
- Conversion from source SVG to raw pixel data happens via a **one-time
  developer-run script**, not as part of the Buildroot image build —
  avoids adding any new host-side build dependency (no `host-librsvg`,
  no `host-cairo`) for something that only needs to run again if an icon
  is ever replaced. This mirrors the original `cs-hud`'s own
  `convert_png_to_ch.py`, except that conversion happened as a
  Buildroot-external offline step there too, judging by the generated
  `icon.c`/`icon.h` being committed source rather than regenerated by
  `cs-hud`'s Docker build. All nine source icons are now SVG (the two
  hand-drawn additions match the battery/WiFi format), so the script
  needs only one rasterization path, not a PNG branch as well.
- Both the source SVG files and the generated C output get committed to
  the repo, so a future icon swap is just "replace the source file,
  re-run the script, commit the diff."

## Architecture

```
tools/convert-icons.py (new, developer-run, NOT part of the Buildroot
build; Python + a Python SVG rasterizer, e.g. CairoSVG)
  |
  | reads source art from:
  |   package/batocera/utils/circuitsword-quickmenu/icons/src/
  |     battery-25.svg, battery-50.svg, battery-75.svg, battery-full.svg,
  |     battery-empty.svg, battery-charging.svg, wifi.svg,
  |     volume.svg, brightness.svg
  |   (battery/wifi SVGs copied verbatim from batocera-emulationstation's
  |   resources/ at the same commit the project's own .mk already pins;
  |   volume/brightness SVGs are new, hand-drawn to match -- same 16x16
  |   viewBox, flat white fill/stroke, reviewed against a rendered preview
  |   before being finalized)
  |
  | rasterizes every icon to one fixed target size (ICON_SIZE x ICON_SIZE,
  | value decided in the implementation plan based on the on-screen line
  | height both overlays already use), extracts the alpha channel only
  | (every source is a flat single-color silhouette -- alpha is the only
  | information that matters, color is supplied at draw time exactly like
  | the previous bitmap-icon scheme already did)
  v
package/batocera/utils/circuitsword-quickmenu/qm_icon_data.c (generated,
committed): one `static const uint8_t` alpha array + width/height per
icon, nine icons total (6 battery states, wifi, volume, brightness)
  |
  | consumed by
  v
qm_icons.c (existing file, rewritten): qm_draw_icon_rgba(fb, x, y,
qm_icon_kind kind, uint32_t color) replaces the old qm_draw_icon() --
per-pixel alpha blend of `color` over the framebuffer, no runtime
scaling (icons are already baked to their final on-screen size)
  |
  | consumed by
  v
quickmenu.c's qm_render() (icon + bar same row, see Layout below)
sb_render.c (unchanged layout, just switches which draw call it makes)
```

## Components

### `tools/convert-icons.py` (new)

Developer-run, not part of `circuitsword-quickmenu`'s Buildroot package
build. Takes the nine SVG source files from `icons/src/`, rasterizes each
to `ICON_SIZE x ICON_SIZE`, extracts the alpha channel, and writes
`qm_icon_data.c` with one array + `{width, height}` struct per icon.
Re-run manually whenever a source icon is replaced; its output is
committed like any other generated-but-tracked source file (comparable to
how a `.proto`-generated file might be committed for a project that
doesn't want a codegen step in its normal build).

### `qm_icon_data.c` (new, generated+committed)

Nine icons: `QM_ICON_BATTERY_25`, `_50`, `_75`, `_FULL`, `_EMPTY`,
`_CHARGING`, `QM_ICON_WIFI`, `QM_ICON_VOLUME`, `QM_ICON_BRIGHTNESS` — the
`qm_icon_kind` enum grows from the previous design's 6 members to these 9
(battery is no longer a 4-level `(kind, level)` pair; it's one kind per
state, matching the source art 1:1 — simpler, and the `qm_icon_level_from_percent()`
0-24/25-49/50-74/75-100 mapping is replaced by a direct state-boundary
mapping using ES's own 5 tiers: `<10 -> EMPTY`, `<35 -> 25`, `<60 -> 50`,
`<85 -> 75`, else `FULL`, with charging always selecting `_CHARGING`
regardless of percent — same "charging replaces rather than overlays"
choice the previous design made, still applies).

### `qm_icons.c` (rewritten)

`qm_draw_icon_rgba(qm_fb *fb, int x, int y, qm_icon_kind kind, uint32_t color)`:
looks up the icon's alpha array + dimensions from `qm_icon_data.c`, and
for every pixel, blends `color` over the existing framebuffer pixel by
the icon's alpha value at that position (`out = bg + (color - bg) * alpha / 255`
per channel) — a straightforward alpha-over compositing operation, no
external library needed (same "no toolkit" constraint as the rest of this
project's rendering code). `qm_icon_level_from_percent()` (from the
previous design) is removed — no longer meaningful now that volume/
brightness are single static icons and battery uses direct state
boundaries instead of a generic 0-3 level.

### `quickmenu.c` (modified — layout change)

Currently: icon draws at row `y`, the percentage bar draws below it at
`y + line_h - 2*scale` (stacked, two visual rows per menu item). New
layout: icon draws at `(margin, y)`, the bar draws immediately to its
right on the same row (`x = margin + ICON_SIZE + gap`), vertically
centered against the icon's height (`y + (ICON_SIZE - bar_h) / 2`). Row
height shrinks accordingly since each item is now one visual line instead
of two — exact pixel arithmetic is an implementation-plan detail, not a
design-level one, since it depends on the final `ICON_SIZE` chosen. WiFi's
row (no bar) is unaffected beyond swapping to the new icon draw call.

### `sb_render.c` (modified — draw call only, no layout change)

Already a single row of 4 icons left-to-right; only the draw call
(`qm_draw_icon` → `qm_draw_icon_rgba`, plus picking one of the 6 new
battery-state icons instead of a `(kind, level)` pair) changes. Margin/gap
arithmetic gets recomputed for the new `ICON_SIZE` (same kind of
recompute the previous design already did once for the bitmap-icon
transition).

## Data Flow

No change to what data feeds the icons — `qm_wifi_get()`/`qm_volume_get()`/
`qm_brightness_get()`/`qm_battery_get()` (already existing) still supply
the same values. Only which icon gets selected changes: battery now maps
percent+charging directly to one of 6 states instead of a generic 0-3
level; WiFi picks the same `QM_ICON_WIFI` for both states, varying only
`color` (`QM_COLOR_FG` vs `QM_COLOR_DIM`); volume/brightness always draw
their one respective icon, unconditionally.

## Error Handling

No change from the previous design's conventions: an out-of-range/
unrecognized `qm_icon_kind` no-ops in `qm_draw_icon_rgba` (same defensive
default the bitmap version had); upstream `qm_*_get()` failures are
already handled by each caller before an icon is ever selected, untouched
by this design.

## Testing

**Verifiable off-device**: `qm_draw_icon_rgba()`'s alpha-blend math (a
few hand-computed pixel values: alpha 0 leaves background untouched,
alpha 255 becomes exactly `color`, alpha 128 lands roughly halfway) and
that every one of the 9 icons draws at least one non-background pixel —
same style of host-`cc`-compiled test `tests/test_qm_icons.c` already
uses, adapted for the new function signature and data source. The battery
percent→state boundary mapping (0, 9, 10, 34, 35, 59, 60, 84, 85, 100,
plus charging-overrides-percent) as pure-function boundary tests, same
style as the previous design's `qm_icon_level_from_percent` tests.

**Needs on-device validation**: visual quality/legibility of the real
icons at actual DPI panel size (the whole point of this change — expected
to be a major improvement over the previous pixel art, but not confirmed
until seen); the new same-row icon+bar layout's proportions on the real
screen; whether `ICON_SIZE` (chosen during implementation) reads clearly
at both the 640px and 320px panel scales.

## Addendum: title wordmark + button badges

Added after the initial design was approved, before implementation
started — folded in here rather than a separate doc since it reuses the
exact same conversion pipeline and draw primitive.

**Title**: `quickmenu.c`'s `"CIRCUIT-SWORD"` title (currently drawn with
`qm_draw_text`'s 5×7 bitmap font) becomes a baked vector-text asset
through the same SVG→alpha-mask pipeline as the icons — sharper, not a
redesigned logo/wordmark. English text stays English (this was already
the case for the title and every menu label — this design only changes
how it's rendered, not its language or copy). One real tradeoff, accepted:
unlike the icon SVGs (pure vector paths, identical on any machine), the
title's source SVG uses an `<text>` element, so its exact rendered shape
depends on which font is installed on whoever runs
`tools/convert-icons.py` — a one-time, developer-machine concern, not
something that affects the shipped binary or runs on-device.

**Button badges**: the hint line (`"A: SELECT   B: BACK   LEFT/RIGHT:
ADJUST"`, also currently `qm_draw_text`) gets a small icon-style badge in
front of each control name — A, B, and LEFT/RIGHT all get one, for a
uniform hint line rather than only the two the user first named. Each
badge is a filled circle in `QM_COLOR_BAR_FG` (the same red accent
already used for the percentage bar fill) with the letter or a directional
triangle cut out via an SVG `<mask>` — the background shows through the
cutout shape. This keeps every baked asset single-color (the same
"alpha-only, color supplied at draw time" model the icons already use) —
a two-color badge (filled circle *and* a contrasting-color letter) was
considered and explicitly rejected to avoid extending the pipeline for
one feature.

**Data model change**: the title wordmark is wide and short, not square
like the 9 existing 20×20 icons, so `qm_icon_asset` gains `width`/`height`
fields (previously implicit via the fixed `QM_ICON_SIZE`) — the 9
existing icons are unaffected (still 20×20, just now expressed
explicitly instead of implicitly), the badges stay 20×20 like the icons,
and only the title asset uses a different size. `qm_draw_icon_rgba`
reads the asset's own width/height instead of assuming `QM_ICON_SIZE`
for every draw call.

Confirmed with the user via a rendered browser preview (same page used
for the original icon review) before finalizing.

## Out of Scope (this phase)

- WiFi signal-strength tiers — still boolean on/off, matches the single
  available source icon (`network.svg` has no signal-strength variants
  either, same limitation the previous pixel-icon design already had).
- Any new icon for mute — volume stays a single static icon regardless of
  level, consistent with the "icon + bar, not icon-encodes-level" choice
  for this whole slot.
- Runtime SVG rendering — explicitly rejected; all rasterization happens
  once, offline, via the developer-run conversion script. No SVG/image
  decode library is linked into either overlay binary.
- Buildroot-side icon regeneration — the conversion script is not wired
  into `circuitsword-quickmenu.mk`/`circuitsword-statusbar.mk`; both
  packages keep compiling the already-generated, already-committed
  `qm_icon_data.c` exactly like any other source file.
